# Incident workflow contract

- Student submission remains owned by the existing complaint form and POST /api/complaints. Each report belongs to its author; incident summaries expose aggregate counts, not other students' identities.
- Student IDs must be `VTU` plus exactly five digits; staff IDs must be `TTS` plus exactly five digits. Each account's email must match its ID at `@veltech.edu.in`. Students choose Day scholar or Hostel; a hostel selection is required only for Hostel residents. Day scholars are stored as `Day Scholar` in the existing residence field.
- Deleting a complaint is a soft delete. It leaves normal queues and exports, while the student can see their own deleted complaints and department staff can see deleted complaints assigned to their department. Deletion metadata and complaint history are retained; deleted records cannot be updated through active complaint routes.
- Complaint relevance is checked by the server before analysis lookups, department routing, incident matching, or persistence. Clear personal-advice requests are rejected; campus service issues and safety/student-conduct reports remain eligible. Ambiguous descriptions are asked to include the campus issue and location, and the form preserves entered text.
- Matching requires the same routed department, normalized location, related issue and a ten-minute window anchored to the first report. Missing locations do not auto-merge. Existing historical records are not retrospectively merged.
- Twenty distinct students trigger Critical priority and an immediate SLA deadline. Repeated reports by one student do not inflate affected counts. Critical incidents sort first in the staff queue.
- public/Script.js owns incidentSummary, incidentReports and consolidateTickets. Student lists retain each personal report; staff lists show one card per incident and disclose linked reports. Filters continue to operate on report data before consolidation.
- Staff update controls explicitly say Update incident. Stage, note, category and priority updates apply to all linked complaints; history is recorded for each member. Existing save/error and refresh behavior remains owned by submitAdminStageUpdate.
- Native select remains the established priority control. Native details/summary owns the linked-report disclosure; it must work using keyboard and at narrow widths. Existing global styles own focus and responsive behavior.
- Deleting a report affects only that report, refreshes aggregate counts and selects a surviving representative. An escalation already raised is not automatically withdrawn by deletion.
- Staff can export one Excel row per active complaint routed to their department; the super admin can export all active complaints. Both exports are server-authorized, exclude image payloads and student contact details, and report download failures through the shared toast.
- The super admin's Student complaints view uses paged, server-side name/College ID search and active complaint counts grouped by student account. Expanding a student loads active complaint titles, descriptions, department, priority, status, and date in pages; the list endpoints omit email, hostel, and photo payloads. The existing complaint detail modal fetches its full record only after an authorized super-admin opens it.
- The super-admin All complaints view is paginated (50 records per page). Complaint IDs are passed to actions through escaped data attributes and event listeners, not inline JavaScript.
- Student, staff and super-admin sidebars are fixed to the viewport and do not scroll independently; main content scrolls beside them. Super-admin Log out is the final sidebar item. The three-bar menu control is shown only at the mobile breakpoint (700px and below); wider layouts keep the sidebar visible.
- Staff updates return the updated complaint and refresh incident cards from local state, avoiding a second full department-list request. Similar-resolution recommendations search only the latest 150 resolved records in the staff member's department.
- Complaint submission runs independent routing, code generation and duplicate-candidate reads concurrently. AI and incident matching candidate queries exclude photo data; the initial complaint and its history entry are written in the same transaction. Student list and submission responses omit the photo payload, which the current UI does not display.
- Initial session restoration uses one endpoint. The page loader is dismissed when static page resources finish loading rather than waiting for the database session check.
- Page navigation uses separate URLs and HTML documents: `/` for landing and student authentication, `/student` for the student dashboard, `/staff` for department staff authentication and dashboard, and `/admin` for super-admin authentication and dashboard. Shared scripts, styles, modal, and toast behavior stay consistent across these documents. A student session opens `/student`; a staff session opens `/staff`; unauthenticated visits to `/student` return to `/`.
- Navigable pages use a page-specific document title in the `{Page} — Complaint Box` format. API endpoints remain under `/api`; page routes do not replace or alter them.
- Complaint-to-department assignment remains based on the category selected in the student form; changing page URLs does not change complaint routing.
- Student complaint and staff incident summary cards are keyboard-accessible buttons that filter their respective lists by status. The total card clears the status filter, while category filters and search remain available. Super-admin summary cards navigate to the matching staff list or department credential view.
- MongoDB transactions serialize complaint creation, incident updates and report deletion across server instances. Use MongoDB Atlas or a replica set.
